## SAA（ソリューションアーキテクト アソシエイト）

### 頻出ポイント

#### 1. EMR基本概念

```yaml
出題パターン:
  「大規模データをSparkで処理したい」

正解アプローチ:
  - Amazon EMR使用
  - Sparkアプリケーション
  - S3でデータ保存
  - EMRFS活用

キーワード:
  ✅ Hadoop / Spark → EMR
  ✅ 大規模データ処理 → EMR
  ✅ 機械学習（MLlib） → EMR Spark
  ✅ マネージドクラスター → EMR
```

#### 2. ノード構成

```yaml
シナリオ:
  「コスト効率的なEMRクラスター構成」

正解:
  Master Node:
    - 1台（小規模）
    - 3台（HA構成、本番）
    - 管理・調整のみ
  
  Core Node:
    - データ保存（HDFS）
    - タスク実行
    - オンデマンド推奨
    - 最小限に
  
  Task Node:
    - タスク実行のみ
    - データ保存なし
    - Spot Instance推奨
    - コスト削減

ポイント:
  ❌ Core NodeにSpot → データ損失リスク
  ✅ Task NodeにSpot → 安全・コスト削減
```

#### 3. ストレージ選択

```yaml
問題:
  「クラスター終了後もデータを保持」

回答:
  S3（EMRFS）:
    - クラスター外保存
    - 永続化
    - 耐久性99.999999999%
    - コスト効率
  
  HDFS:
    - クラスター内のみ
    - 終了時削除
    - 中間データ向き

設計:
  入力: S3
  処理: HDFS（中間データ）
  出力: S3
```

#### 4. コスト最適化

```yaml
シナリオ:
  「EMRコスト削減方法」

正解:
  Spot Instance:
    - Task Node活用
    - 最大90%削減
    - 中断許容
  
  一時的クラスター:
    - ジョブ単位起動
    - 処理完了後終了
    - 自動化
  
  適切なサイジング:
    - 過剰プロビジョニング避ける
    - モニタリング
  
  S3活用:
    - HDFS削減
    - Core Node最小化

キーワード:
  ✅ コスト削減 → Spot Instance（Task Node）
  ✅ 未使用時停止 → 一時的クラスター
```

## SAP（ソリューションアーキテクト プロフェッショナル）

### 高度なシナリオ

#### 1. EMR vs Glue vs Athena

```yaml
要件分析:

Amazon Athena:
  適用:
    - アドホックSQL分析
    - サーバーレス
    - 即座に開始
    - 小〜中規模クエリ
  
  制限:
    - SQLのみ
    - カスタマイズ不可
    - 複雑な処理困難
  
  コスト:
    - スキャンデータ量課金
    - $5/TB

AWS Glue:
  適用:
    - 標準的なETL
    - サーバーレス
    - 簡単なSpark
    - 小〜中規模
  
  制限:
    - Spark設定制限
    - インタラクティブ不可
    - 複雑な処理困難
  
  コスト:
    - DPU時間課金
    - $0.44/DPU時間

Amazon EMR:
  適用:
    - 複雑な処理
    - 大規模データ
    - カスタマイズ必要
    - 機械学習
    - 継続的処理
  
  制限:
    - クラスター管理必要
    - 起動時間
    - 運用負荷
  
  コスト:
    - EC2 + EMR料金
    - 長時間実行で効率的

選択基準:
  単純SQLクエリ（月1回）:
    → Athena
    理由: サーバーレス、即座、コスト効率
  
  標準ETL（日次）:
    → Glue
    理由: サーバーレス、管理不要
  
  大規模機械学習（週次、TB級）:
    → EMR
    理由: Spark MLlib、カスタマイズ、コスト効率
  
  複雑なストリーミング処理:
    → EMR
    理由: Spark Streaming、柔軟性
  
  継続的分析（24時間）:
    → EMR
    理由: 長時間実行で効率的、インタラクティブ
```

#### 3. ストリーミング分析

```yaml
要件:
  「IoTデータをリアルタイム処理、秒単位レイテンシ」

アーキテクチャ:
  データ収集:
    IoTデバイス（100万台）
      ↓
    Kinesis Data Streams:
      - シャード数: 100
      - 拡張ファンアウト
      ↓
  
  リアルタイム処理:
    EMR Spark Streaming:
      クラスター:
        - Master: 3台（HA）
        - Core: 10台
        - Task: 20-40台（Auto Scaling）
      
      処理:
        - マイクロバッチ（5秒）
        - ウィンドウ集計
        - 異常検知
        - データエンリッチメント
      
      チェックポイント:
        - S3バケット
        - 5秒間隔
        - 障害回復
      ↓
  
  出力:
    DynamoDB:
      - 最新値（低レイテンシ読み込み）
      - TTL設定
    
    S3:
      - 全履歴（Parquet）
      - パーティション（date/hour）
      - 長期分析
    
    CloudWatch:
      - カスタムメトリクス
      - リアルタイムダッシュボード
  
  バッチ分析:
    S3履歴データ
      ↓
    EMR Spark Batch（日次）:
      - 詳細分析
      - 機械学習モデル更新
      - 集計レポート
      ↓
    Redshift / Athena

スケーリング:
  Kinesis:
    - Auto Scaling
    - シャード数調整
  
  EMR:
    - Task Node Auto Scaling
    - ContainerPendingRatio
    - YARNMemoryAvailable
  
  DynamoDB:
    - オンデマンドキャパシティ
    - またはAuto Scaling

レイテンシ:
  データ収集 → Kinesis: <1秒
  Kinesis → EMR処理: 5秒（マイクロバッチ）
  EMR → DynamoDB: <1秒
  
  合計: 6-7秒（エンドツーエンド）

コスト最適化:
  - Task NodeにSpot（60%削減）
  - DynamoDBオンデマンド（予測困難）
  - S3 Intelligent-Tiering
```

## よくある間違い

### 間違い 1: ストレージの誤解

```yaml
❌ 誤り:
  「HDFSがEMRの主要ストレージ」

✅ 正解:
  S3（EMRFS）推奨:
    - クラスター外永続化
    - 耐久性高い
    - コスト効率
    - データ共有容易
  
  HDFS用途:
    - 中間データ
    - 頻繁アクセス
    - 高スループット

設計:
  入力: S3
  処理: HDFS（一時）
  出力: S3
```

### 間違い 2: Spotの誤解

```yaml
❌ 誤り:
  「Core NodeにSpot使用でコスト削減」

✅ 正解:
  Task NodeにSpot:
    - データ保存なし
    - 中断影響最小
    - 安全
  
  Core Nodeはオンデマンド:
    - HDFSデータ保存
    - 中断時データ損失
    - リスク高い

例外（上級）:
  - HDFSレプリケーション増加
  - S3バックアップ
  - リスク許容
```

### 間違い 3: サービス選択の誤解

```yaml
❌ 誤り:
  「EMRは常にGlueより優れている」

✅ 正解:
  使い分け:
    簡単なETL（日次、GB級）:
      → Glue
      理由: サーバーレス、管理不要
    
    複雑な処理（TB級、機械学習）:
      → EMR
      理由: カスタマイズ、大規模、効率的
    
    アドホックSQL:
      → Athena
      理由: 即座、サーバーレス

組み合わせ:
  - Glue Crawler（メタデータ）
  - EMR（大規模処理）
  - Athena（アドホック分析）
```

### 間違い 4: クラスター設計の誤解

```yaml
❌ 誤り:
  「Master Nodeを大きくすれば高速化」

✅ 正解:
  Master Node:
    - 管理・調整のみ
    - 小〜中サイズで十分
    - 大規模化不要
  
  高速化:
    - Core/Task Node増強
    - 適切なインスタンスタイプ
    - Spark設定最適化
    - データパーティション

適切な設計:
  小規模:
    Master: 1 × m5.xlarge
    Core: 3 × m5.2xlarge
  
  大規模:
    Master: 3 × m5.xlarge（HA）
    Core: 20 × m5.4xlarge
    Task: 50 × m5.4xlarge（Spot）
```

### 間違い 5: HA構成の誤解

```yaml
❌ 誤り:
  「EMRは自動的に高可用性」

✅ 正解:
  デフォルト:
    - Master: 1台
    - Single Point of Failure
  
  HA構成:
    - Master: 3台
    - 自動フェイルオーバー
    - 明示的設定必要
  
  推奨:
    本番環境:
      - Master 3台
      - 複数AZ
      - S3でデータ永続化
    
    開発環境:
      - Master 1台
      - コスト優先
```
