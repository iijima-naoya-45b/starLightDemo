## 主要ユースケース

### 1. ログ分析

```yaml
シナリオ:
  - Webサーバー・アプリケーションログ分析
  - アクセスログ解析
  - セキュリティログ監査
  - ユーザー行動分析

アーキテクチャ:
  データ収集:
    Kinesis Data Firehose
      ↓
    S3バケット（生ログ）
      - Parquet形式変換
      - パーティション（date/hour）
  
  EMR処理:
    Spark Job:
      - ログパース
      - データクレンジング
      - 集計・フィルタリング
      - 異常検知
      ↓
    S3（処理済み）
  
  可視化:
    - Athena でアドホック分析
    - QuickSight でダッシュボード
    - EMR Presto でインタラクティブ分析

メリット:
  - 大量ログ高速処理
  - リアルタイム・バッチ両対応
  - スケーラブル
  - コスト効率

実装例:
  処理内容:
    - アクセスログ集計
    - エラー率計算
    - レスポンスタイム分析
    - ユーザーセッション追跡
  
  頻度:
    - 時間毎バッチ
    - 日次サマリー
```

### 2. 機械学習パイプライン

```yaml
シナリオ:
  - 大規模データ前処理
  - 特徴量エンジニアリング
  - モデル学習
  - 予測バッチ処理

アーキテクチャ:
  データ準備:
    S3（生データ）
      ↓
    EMR Spark:
      - データクレンジング
      - 特徴量抽出
      - データ正規化
      - トレーニング/テストデータ分割
      ↓
    S3（前処理済み）
  
  モデル学習:
    Spark MLlib:
      - 分散学習
      - ハイパーパラメータチューニング
      - クロスバリデーション
      ↓
    S3（モデル保存）
  
  推論:
    SageMaker:
      - リアルタイム推論
    
    または
    
    EMR Spark:
      - バッチ推論
      - 大量データスコアリング

用途:
  推薦システム:
    - 協調フィルタリング
    - コンテンツベースフィルタリング
    - ALS（Alternating Least Squares）
  
  異常検知:
    - クラスタリング
    - 外れ値検出
    - 時系列分析
  
  分類・回帰:
    - ランダムフォレスト
    - 勾配ブースティング
    - ロジスティック回帰
```

### 3. ETL処理

```yaml
シナリオ:
  - 複数ソースからのデータ統合
  - データ変換・正規化
  - データウェアハウスへロード
  - データレイク構築

アーキテクチャ:
  抽出（Extract）:
    複数ソース:
      - S3（ログ、CSV）
      - RDS（トランザクション）
      - DynamoDB（NoSQL）
      - 外部API
      ↓
    EMR Spark:
      - データ読み込み
      - 並列抽出
  
  変換（Transform）:
    EMR処理:
      - データクレンジング
      - 重複排除
      - データ正規化
      - ビジネスロジック適用
      - 集計・結合
      - フォーマット変換（Parquet）
  
  ロード（Load）:
    Redshift:
      - データウェアハウス
      - COPY コマンド
      - S3経由ロード
    
    または
    
    S3 Data Lake:
      - Parquet形式
      - パーティション構造
      - Athena/Presto分析

スケジュール実行:
  - EventBridge Scheduler
  - Step Functions
  - MWAA（Airflow）

データ品質:
  - スキーマ検証
  - NULL値チェック
  - データ型確認
  - 統計情報計算
```

### 4. データレイク構築

```yaml
シナリオ:
  - 全社データ統合基盤
  - 様々なデータソース集約
  - スケーラブルなストレージ
  - 柔軟な分析基盤

アーキテクチャ（ラムダアーキテクチャ）:
  
  バッチレイヤー:
    S3（Raw Data）
      ↓
    EMR Hadoop/Spark:
      - 大規模バッチ処理
      - 履歴データ処理
      - マスターデータセット作成
      ↓
    S3（Processed/Parquet）
  
  スピードレイヤー:
    Kinesis Data Streams
      ↓
    EMR Spark Streaming:
      - リアルタイム処理
      - 増分更新
      - 低レイテンシ
      ↓
    DynamoDB/S3
  
  サービングレイヤー:
    Athena:
      - インタラクティブクエリ
      - Glue Data Catalog
    
    Redshift Spectrum:
      - 高速クエリ
      - S3直接スキャン
    
    EMR Presto:
      - 複雑な分析
      - アドホッククエリ

データゾーン:
  Raw Zone:
    - 生データ
    - 変更なし
    - 長期保存
  
  Processed Zone:
    - クレンジング済み
    - Parquet形式
    - パーティション
  
  Curated Zone:
    - ビジネス向け
    - 集計済み
    - 最適化

Lake Formation統合:
  - 一元管理
  - アクセス制御
  - データカタログ
  - セキュリティ
```

## アーキテクチャパターン

### パターン1: バッチ処理（一時的クラスター）

```yaml
概要:
  - ジョブ実行時のみクラスター起動
  - 処理完了後自動終了
  - コスト最適

構成:
  トリガー:
    EventBridge Schedule
      ↓
    Lambda
      - EMRクラスター作成
      - ステップ送信
  
  EMRクラスター:
    Master: 1台
    Core: 3台
    Task: 10台（Spot Instance）
    
    ステップ:
      1. データ前処理
      2. メイン処理
      3. 結果保存
      4. クリーンアップ
    
    自動終了:
      - 全ステップ完了後
      - または失敗時
  
  通知:
    SNS:
      - 成功通知
      - 失敗アラート

メリット:
  - コスト最小
  - 自動化容易
  - スケーラブル

デメリット:
  - 起動時間（5-10分）
  - インタラクティブ不可
```

### パターン2: 長時間実行クラスター

```yaml
概要:
  - 常時起動クラスター
  - インタラクティブ分析
  - 複数ジョブ実行

構成:
  EMRクラスター:
    Master: 3台（HA構成）
    Core: 5台
    Task: Auto Scaling（5-20台）
    
    アプリケーション:
      - Spark
      - Presto
      - Hive
      - Hue
      - Zeppelin
  
  アクセス:
    EMR Studio:
      - ノートブック開発
    
    SSH:
      - コマンドライン
    
    Hue:
      - Web UI
  
  データ:
    HDFS:
      - 頻繁アクセスデータ
      - 中間データ
    
    S3:
      - 永続データ
      - 入力/出力

用途:
  - データサイエンス
  - アドホック分析
  - 開発環境
  - プロトタイピング

コスト最適化:
  - Task NodeにSpot
  - Auto Scaling
  - 非業務時間停止
```

### パターン3: マルチテナント（EMR on EKS）

```yaml
概要:
  - 複数チームでEKSクラスター共有
  - 名前空間分離
  - リソース効率

構成:
  EKSクラスター:
    ノードグループ:
      - 汎用ノード
      - Spot ノード
      - GPU ノード（ML用）
  
  EMR Virtual Clusters:
    チームA:
      - Spark Jobsのみ
      - 名前空間: team-a
      - リソースクォータ
    
    チームB:
      - Presto Queries
      - 名前空間: team-b
      - リソースクォータ
  
  実行:
    StartJobRun API:
      - ジョブ送信
      - 動的Pod作成
      - 完了後Pod削除

メリット:
  - リソース効率
  - 運用コスト削減
  - 柔軟なスケーリング
  - 既存EKS活用

ユースケース:
  - 複数部門
  - 開発/本番環境
  - マイクロサービス統合
```

### パターン4: ハイブリッド（EMR + Glue）

```yaml
概要:
  - GlueとEMRの適材適所
  - コスト・柔軟性バランス

使い分け:
  AWS Glue:
    - 簡単なETL
    - スキーマ管理
    - Crawler
    - 小〜中規模データ
  
  Amazon EMR:
    - 複雑な処理
    - カスタムロジック
    - 大規模データ
    - 機械学習

アーキテクチャ:
  定期ETL:
    Glue Crawler
      ↓
    Glue Data Catalog
      ↓
    Glue ETL Job（簡単な変換）
      ↓
    S3
  
  大規模分析:
    S3
      ↓
    EMR Spark（複雑な処理）
      ↓
    S3 / Redshift
  
  メタデータ共有:
    - Glue Data Catalog
    - EMR Hive/Spark統合
    - Athena分析

メリット:
  - 最適コスト
  - 運用負荷最小
  - 柔軟性
```

### パターン5: データレイク + リアルタイム

```yaml
概要:
  - バッチ + ストリーミング
  - 包括的分析基盤

アーキテクチャ:
  バッチ処理:
    S3（履歴データ）
      ↓
    EMR Spark Batch:
      - 日次処理
      - 大規模集計
      - マスターデータ更新
      ↓
    S3 Data Lake
  
  ストリーミング:
    Kinesis Data Streams
      ↓
    EMR Spark Streaming:
      - リアルタイム集計
      - イベント処理
      ↓
    DynamoDB（最新値）
    S3（履歴）
  
  統合ビュー:
    バッチビュー + リアルタイムビュー
      ↓
    Athena / Presto:
      - 統合クエリ
      - 完全なデータビュー

メリット:
  - 完全性（バッチ）
  - 低レイテンシ（ストリーミング）
  - 柔軟な分析
```

### パターン6: セキュアデータ処理

```yaml
概要:
  - 機密データ処理
  - コンプライアンス対応
  - 強固なセキュリティ

アーキテクチャ:
  ネットワーク:
    VPC:
      - プライベートサブネット
      - NATゲートウェイ
      - VPCエンドポイント（S3、DynamoDB）

      - パブリックIP無し

      - EBS: KMS暗号化

      - ノード間TLS
      - S3 HTTPS
  
  認証:
    Kerberos:
      - Active Directory統合

      - アプリケーションレベル

      - テーブルレベル権限
      - 列レベル権限
      - 行レベルフィルタ
  
  監査:
    CloudTrail:
      - API呼び出しログ
      - S3暗号化保存
    
    EMRログ:
      - S3保存
      - 改ざん防止（S3 Object Lock）

ユースケース:
  - 金融データ
  - 医療データ（HIPAA）
  - 個人情報（GDPR）
  - 政府機関
```

## サービス比較

### EMR vs Glue vs Athena

```yaml
選択基準:

Amazon Athena:
  最適:
    - アドホックSQL分析
    - 小〜中規模クエリ
    - サーバーレス希望
    - 即座に開始
  
  制約:
    - SQLのみ
    - カスタマイズ制限
    - 複雑な処理困難
  
  コスト:
    - スキャンデータ量課金
    - $5/TB

AWS Glue:
  最適:
    - 標準的なETL
    - サーバーレス希望
    - 簡単なSparkジョブ
    - 小〜中規模
  
  制約:
    - Spark設定制限
    - 複雑な処理困難
    - インタラクティブ不可
  
  コスト:
    - DPU時間課金
    - $0.44/DPU時間

Amazon EMR:
  最適:
    - 複雑な処理
    - 大規模データ
    - カスタマイズ必要
    - 機械学習
    - 複数フレームワーク
  
  制約:
    - クラスター管理必要
    - 起動時間
    - 運用負荷
  
  コスト:
    - EC2 + EMR料金
    - 長時間実行で効率的
    - Spot活用で大幅削減

使い分け例:
  ログクエリ（月1回）:
    → Athena
  
  日次ETL（標準処理）:
    → Glue
  
  大規模機械学習（週次）:
    → EMR
  
  複雑なストリーミング:
    → EMR
```

### EMR vs EMR Serverless vs EMR on EKS

```yaml
EMR on EC2:
  メリット:
    - 完全制御
    - 全機能利用可能
    - 長時間実行に最適
    - カスタマイズ自由
  
  デメリット:
    - クラスター管理必要
    - 起動時間
  
  適用:
    - 複雑な要件
    - インタラクティブ分析
    - 継続的処理

EMR Serverless:
  メリット:
    - サーバーレス
    - 自動スケーリング
    - ジョブ単位課金
    - 管理不要
  
  デメリット:
    - 機能制限
    - カスタマイズ制限
    - コールドスタート
  
  適用:
    - 定期バッチ
    - 断続的ジョブ
    - シンプルな処理

EMR on EKS:
  メリット:
    - 既存EKS活用
    - マルチテナント
    - Kubernetes統合
    - リソース効率
  
  デメリット:
    - EKS知識必要
    - 複雑性
  
  適用:
    - 複数チーム
    - コンテナ環境
    - マイクロサービス統合
```

## まとめ

**主要ユースケース:**
- ログ分析: 大量ログのバッチ/リアルタイム処理
- 機械学習: Spark MLlibで分散学習
- ETL処理: 複数ソースからデータ統合
- データレイク: S3ベースの全社データ基盤
- ゲノム解析: 大規模並列バイオインフォマティクス
- ストリーミング: Kinesis統合リアルタイム分析

**アーキテクチャパターン:**
- 一時的クラスター: コスト最適、自動化
- 長時間実行: インタラクティブ分析、複数ジョブ
- EMR on EKS: マルチテナント、リソース効率
- ハイブリッド: Glue + EMRの適材適所
- データレイク: バッチ + ストリーミング統合
- セキュア処理: 暗号化、Kerberos、Lake Formation

**サービス選択:**
- Athena: アドホックSQL、小〜中規模
- Glue: 標準ETL、サーバーレス
- EMR: 複雑処理、大規模、カスタマイズ
