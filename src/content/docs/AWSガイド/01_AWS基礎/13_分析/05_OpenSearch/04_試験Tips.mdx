## SAA（ソリューションアーキテクト アソシエイト）

### 頻出ポイント

#### 1. OpenSearch基本概念

```yaml
出題パターン:
  「ログをリアルタイムで分析・検索したい」
  「フルテキスト検索機能を実装したい」

正解アプローチ:
  - Amazon OpenSearch Service
  - リアルタイム分析
  - フルテキスト検索
  - Kibana（OpenSearch Dashboards）で可視化

キーワード:
  ✅ ログ分析 → OpenSearch
  ✅ リアルタイム検索 → OpenSearch
  ✅ フルテキスト → OpenSearch
  ✅ Elasticsearch互換 → OpenSearch
  ❌ SQLクエリのみ → Athena
  ❌ データウェアハウス → Redshift
```

#### 2. OpenSearch vs CloudWatch Logs

```yaml
シナリオ:
  「ログ分析方法の選択」

OpenSearch:
  用途:
    - 複雑な検索クエリ
    - 集計・分析
    - ダッシュボード可視化
    - 長期保存・検索
  
  特徴:
    - フルテキスト検索
    - 高度な集計
    - カスタムダッシュボード
    - 時系列分析
  
  コスト:
    - インスタンス稼働
    - ストレージ課金
    - 継続的コスト

CloudWatch Logs:
  用途:
    - 基本的なログ収集
    - シンプルなフィルタリング
    - メトリクスフィルタ
    - アラート
  
  特徴:
    - AWS統合簡単
    - 基本的な検索
    - メトリクス変換
    - アラーム連携
  
  コスト:
    - ログ取り込み課金
    - ストレージ課金
    - クエリ実行課金

選択基準:
  CloudWatch Logs:
    - シンプルなログ収集・監視
    - 基本的なフィルタリング
    - コスト重視（少量）
  
  OpenSearch:
    - 複雑な分析・検索
    - ダッシュボード必要
    - 長期保存・分析
    - 大量ログ（UltraWarm活用）
```

#### 3. 可用性設計

```yaml
問題:
  「OpenSearchの高可用性構成」

回答:
  Multi-AZ:
    - 3つのAZ推奨
    - ノード自動配置
    - 自動フェイルオーバー
  
  専用マスターノード:
    - 3台（奇数）必須
    - クラスター安定性
    - スプリットブレイン防止
  
  レプリカ:
    - 最低1レプリカ
    - 異なるAZに配置
    - データ保護

構成例:
  - データノード: 3台以上（Multi-AZ）
  - マスターノード: 3台
  - レプリカ: 1以上
```

#### 4. データ取り込み

```yaml
シナリオ:
  「ログをOpenSearchに取り込む方法」

方法1（CloudWatch Logs）:
  CloudWatch Logs
    → Lambda（サブスクリプションフィルタ）
    → OpenSearch
  
  用途:
    - AWSサービスログ
    - Lambda/ECS/EC2ログ
    - 変換・フィルタリング

方法2（Kinesis Firehose）:
  アプリケーション
    → Kinesis Data Firehose
    → Lambda（変換、オプション）
    → OpenSearch
  
  用途:
    - ストリーミングデータ
    - スケーラブル
    - 自動再試行
    - S3バックアップ

方法3（Logstash/Beats）:
  サーバー
    → Logstash/Beats
    → OpenSearch
  
  用途:
    - オンプレミス
    - 複雑な変換
    - 複数ソース統合
```

## SAP（ソリューションアーキテクト プロフェッショナル）

### 高度なシナリオ

#### 1. 大規模ログ分析基盤

```yaml
要件:
  「複数アカウント、数TB/日のログを集約分析」

設計:
  収集層:
    各アカウント:
      - CloudWatch Logs
      - VPC Flow Logs
      - ALB/CloudFront Logs
    
    集約:
      - Kinesis Data Firehose（クロスアカウント）
      - 中央アカウントへ配信
      - Lambda変換・エンリッチメント
  
  OpenSearchクラスター:
    データノード:
      - r6g.2xlarge × 12（4台/AZ）
      - Multi-AZ（3 AZ）
    
    マスターノード:
      - m6g.large × 3
    
    ストレージ戦略:
      Hot（最新7日）:
        - EBS gp3
        - 高頻度検索
      
      Warm（8〜30日）:
        - UltraWarm
        - 定期検索
        - 75%コスト削減
      
      Cold（31〜365日）:
        - コールドストレージ
        - アーカイブ
        - 95%コスト削減
  
  ISMポリシー:
    - 7日後: Warm移行
    - 30日後: Cold移行
    - 365日後: 削除
  
  可視化:
    - OpenSearch Dashboards
    - アカウント別ダッシュボード
    - セキュリティダッシュボード
    - コストダッシュボード
  
  セキュリティ:
    - VPC内配置
    - Fine-grained Access Control
    - 組織単位のロール
    - KMS暗号化

スケーラビリティ:
  - Auto-Tune有効化
  - 水平スケーリング
  - シャード動的調整
```

#### 2. セキュリティ分析プラットフォーム（SIEM）

```yaml
要件:
  「統合セキュリティ分析基盤」

ログソース統合:
  AWS Security Services:
    CloudTrail:
      - 全APIコール監査
      - S3 → Firehose → OpenSearch
    
    GuardDuty:
      - 脅威検出
      - EventBridge → Lambda → OpenSearch
    
    Security Hub:
      - 統合セキュリティ知見
      - EventBridge → OpenSearch
    
    VPC Flow Logs:
      - ネットワークトラフィック
      - Athena分析 + OpenSearch
    
    WAF:
      - Web攻撃ログ
      - Kinesis Firehose → OpenSearch
  
  アプリケーション:
    - 認証ログ
    - アクセスログ
    - Kinesis Firehose

データモデル:
  インデックス設計:
    security-cloudtrail-{YYYY.MM.DD}
    security-guardduty-{YYYY.MM.DD}
    security-waf-{YYYY.MM.DD}
    security-vpc-flow-{YYYY.MM.DD}
  
  共通フィールド:
    - @timestamp
    - event_type
    - severity
    - source_ip
    - user_identity
    - resource
    - action

相関分析:
  クエリ例:
    # 異常なAPI呼び出し後のネットワーク活動
    - CloudTrailの異常なAssumeRole
    - 同時刻のVPC Flow Logs分析
    - GuardDutyアラート相関

ダッシュボード:
  セキュリティオペレーションセンター:
    - リアルタイム脅威マップ
    - 重大度別イベント
    - トップ攻撃者IP
    - 異常行動検出
  
  コンプライアンス:
    - 特権アクセス監査
    - 設定変更履歴
    - データアクセスログ

アラート:
  高優先度:
    - GuardDuty重大な検出
    - ルートアカウント使用
    - IAMポリシー変更
    - セキュリティグループ変更
    - 大量データ流出
  
  アクション:
    - SNS → PagerDuty/Slack
    - Lambda自動対応
      - セキュリティグループ隔離
      - IAMキー無効化
      - インシデントチケット作成
```

#### 3. ハイブリッドログ分析

```yaml
要件:
  「オンプレミスとAWSの統合ログ分析」

アーキテクチャ:
  オンプレミス:
    Logstash/Beats:
      - アプリケーションサーバー
      - データベース
      - ネットワーク機器
    
    転送:
      - Direct Connect / VPN
      - TLS暗号化
      - VPCエンドポイント経由
  
  AWS:
    CloudWatch Logs:
      - AWSサービス
    
    統合:
      - すべてOpenSearchへ
  
  OpenSearch:
    - VPC内配置
    - ハイブリッド接続
    - 統一ダッシュボード

セキュリティ:
  - Direct Connect（専用線）
  - VPN（暗号化）
  - VPCエンドポイント
  - プライベート接続のみ
  - Fine-grained Access Control

メリット:
  - 統一分析基盤
  - ハイブリッド可視化
  - 相関分析
  - 段階的移行可能
```

## よくある間違い

### 間違い 1: リアルタイム性の誤解

```yaml
❌ 誤り:
  「OpenSearchは完全リアルタイム」

✅ 正解:
  準リアルタイム（Near Real-Time）:
    - refresh_interval: 1秒（デフォルト）
    - インデックス作成後、最大1秒で検索可能
    - 完全リアルタイムではない
  
  真のリアルタイム:
    - Kinesis Data Analytics
    - サブミリ秒レイテンシ必要なら別の選択肢
```

### 間違い 2: 用途の誤解

```yaml
❌ 誤り:
  「OpenSearchはプライマリデータストア」

✅ 正解:
  - 検索・分析エンジン
  - セカンダリデータストア
  - プライマリデータは別に保存
  
  正しい構成:
    RDS/DynamoDB（プライマリ）
      ↓ 同期
    OpenSearch（検索・分析）
```

### 間違い 3: スケーリングの誤解

```yaml
❌ 誤り:
  「OpenSearchは自動スケール」

✅ 正解:
  - 手動スケーリング
  - インスタンス追加/削除は手動
  - Auto Tuneは設定最適化のみ
  
  Serverless:
    - OpenSearch Serverless
    - 自動スケール対応
    - 用途限定的
```

### 間違い 4: サービス比較の誤解

```yaml
OpenSearch vs Athena:
  ❌ 誤り: 
    「ログ分析はすべてOpenSearch」
  
  ✅ 正解:
    OpenSearch:
      - リアルタイム検索
      - 複雑なクエリ
      - ダッシュボード
      - インフラ管理必要
    
    Athena:
      - アドホック分析
      - S3データ直接
      - サーバーレス
      - SQLのみ

OpenSearch vs CloudWatch Logs:
  ❌ 誤り:
    「CloudWatch Logsは不要」
  
  ✅ 正解:
    CloudWatch Logs:
      - 基本的な収集・監視
      - AWS統合簡単
      - シンプル・低コスト
    
    OpenSearch:
      - 高度な分析
      - カスタムダッシュボード
      - 長期保存・検索

OpenSearch vs Redshift:
  ❌ 誤り:
    「データウェアハウスにOpenSearch」
  
  ✅ 正解:
    OpenSearch:
      - 検索・ログ分析
      - リアルタイム
      - フルテキスト
    
    Redshift:
      - データウェアハウス
      - 大規模集計
      - SQL分析
      - BI統合
```

### 間違い 5: セキュリティの誤解

```yaml
❌ 誤り:
  「パブリックアクセスで本番運用」

✅ 正解:
  本番環境:
    - VPC内配置必須
    - パブリックアクセス無効
    - Fine-grained Access Control
    - KMS暗号化
    - TLS/SSL
  
  開発環境のみ:
    - パブリックアクセス可
    - IPホワイトリスト
```

## まとめ

**試験で押さえるべき重要ポイント:**

SAA:
- OpenSearch = リアルタイムログ分析・検索
- Elasticsearch互換、Kibana可視化
- Multi-AZ + 専用マスターで高可用性
- Kinesis Firehose/CloudWatch Logs統合
- VPC内配置 + Fine-grained Access Control

サービス使い分け:
- OpenSearch: 複雑な検索・分析・ダッシュボード
- CloudWatch Logs: シンプルな収集・基本監視
- Athena: S3アドホック分析（SQL）
- Redshift: データウェアハウス・大規模BI

SAP:
- 大規模ログ分析基盤設計
- UltraWarm・Coldストレージでコスト削減（75〜95%）
- セキュリティ分析プラットフォーム（SIEM）
- ISMポリシーでライフサイクル自動化
- マルチアカウント・マルチテナント設計
- ハイブリッド環境統合
- 適切なシャード設計（10〜50GB/シャード）
- Auto-Tune・Gravitonで最適化
