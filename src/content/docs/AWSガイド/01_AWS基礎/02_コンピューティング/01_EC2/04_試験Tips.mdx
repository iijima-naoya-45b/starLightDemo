## EC2 試験Tips (SAA/SAP)

### 頻出トピック

#### 1. インスタンスタイプ選択

```yaml
汎用 (T3, M6i):
  - Webサーバー
  - 中小規模アプリ

コンピューティング最適化 (C6i):
  - バッチ処理
  - HPC
  - ゲームサーバー

メモリ最適化 (R6i, X2iedn):
  - データベース
  - インメモリキャッシュ
  - ビッグデータ処理

ストレージ最適化 (I4i, D3):
  - NoSQL DB
  - データウェアハウス

GPU (P4, G5):
  - 機械学習
  - グラフィックス
```

#### 2. 購入オプション

```yaml
頻出問題パターン:

Q: 予測可能な安定ワークロード、コスト最小化
A: Reserved Instances（1年/3年）

Q: バッチ処理、中断許容、コスト最小化
A: Spot Instances（最大90%割引）

Q: 予測不可能、短期ワークロード
A: On-Demand Instances

Q: 柔軟性とコスト削減の両立
A: Savings Plans
```

#### 3. Auto Scaling

```yaml
スケーリングポリシー:
  ターゲット追跡:
    - CPU使用率維持
    - シンプル、推奨
  
  ステップスケーリング:
    - 段階的スケール
    - 細かい制御
  
  スケジュール:
    - 予測可能な負荷
    - 時間ベース

ヘルスチェック:
  - EC2ステータスチェック
  - ELBヘルスチェック（推奨）
```

#### 4. ストレージ

```yaml
EBS選択:
  gp3:
    - ほとんどのワークロード
    - コスト効率
  
  io2:
    - データベース
    - 高IOPS要求
  
  st1:
    - ビッグデータ
    - ログ処理

インスタンスストア:
  - 一時データ
  - キャッシュ
  - 高速I/O
  - インスタンス停止で消失
```

### 頻出シナリオ問題

#### シナリオ1: 高可用性Webアプリ

```
要件:
- 99.99%可用性
- 自動スケーリング
- コスト最適化

解答:
- ALB（マルチAZ）
- Auto Scaling Group
  - 最小: 2（マルチAZ）
  - 最大: 10
  - ターゲット追跡: CPU 70%
- Reserved Instances（ベースライン2台）
- On-Demand（スパイク対応）

ポイント:
✓ マルチAZ配置
✓ Auto Scaling
✓ RI + On-Demand混在
```

#### シナリオ2: バッチ処理コスト削減

```
要件:
- 夜間バッチ処理
- 中断許容
- コスト最小化

解答:
- Spot Instances
- Spot Fleet（複数インスタンスタイプ）
- チェックポイント保存（S3）
- 中断時自動再開

コスト削減:
- 最大90%割引
```

#### シナリオ3: データベースサーバー

```
要件:
- 高IOPS
- 低レイテンシー
- 高可用性

解答:
- r6i.2xlarge（メモリ最適化）
- EBS io2（プロビジョンドIOPS）
- マルチAZ配置
- ELBヘルスチェック
- 自動フェイルオーバー
```

### よくある間違い

```yaml
× 誤り: 本番環境でSpot Instances単独使用
○ 正解: Spot + On-Demand混在、またはSpot不使用

× 誤り: 全てOn-Demand（予測可能ワークロード）
○ 正解: Reserved Instances活用

× 誤り: 単一AZ配置（高可用性要求）
○ 正解: マルチAZ配置

× 誤り: インスタンスストアに重要データ保存
○ 正解: EBSに保存、定期スナップショット
```
