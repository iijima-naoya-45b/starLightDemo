## App Runner 試験Tips (SAA/SAP)

### 頻出トピック

#### 1. App Runner vs Fargate vs Elastic Beanstalk

```yaml
App Runner:
  特徴:
    - フルマネージド
    - WebアプリAPI特化
    - 自動スケーリング（設定簡単）
    - ソースコード/コンテナ対応
  
  適用:
    - REST API
    - マイクロサービス
    - CI/CD統合重視
    - インフラ管理最小化
  
  制約:
    - リクエスト最大120秒
    - 永続ストレージなし

Fargate:
  特徴:
    - サーバーレスコンテナ
    - ECS/EKS統合
    - より柔軟な設定
    - 汎用コンテナ実行
  
  適用:
    - バッチ処理
    - 長時間実行タスク
    - 複雑なネットワーク構成
    - 既存ECS/EKS環境
  
  設定:
    - タスク定義必要
    - VPC設定必須
    - より複雑

Elastic Beanstalk:
  特徴:
    - プラットフォーム管理
    - 多様な言語対応
    - EC2ベース
    - より高いカスタマイズ性
  
  適用:
    - レガシーアプリ移行
    - EC2機能必要
    - より細かい制御
    - マルチティアアプリ
  
  設定:
    - プラットフォーム選択
    - 環境設定多数
```

#### 2. サービス選択基準

```yaml
頻出問題パターン:

Q: 迅速なWebアプリデプロイ、インフラ管理不要
A: App Runner
理由: フルマネージド、最速デプロイ、設定最小

Q: 既存ECSクラスター統合、複雑なネットワーク構成
A: Fargate
理由: ECS/EKS統合、柔軟な設定

Q: バッチ処理、実行時間2時間
A: Fargate
理由: App Runnerは120秒制限、Fargateは長時間実行可能

Q: レガシーJavaアプリ、Tomcat必要
A: Elastic Beanstalk
理由: プラットフォーム対応、EC2ベース

Q: マイクロサービスAPI、GitHub自動デプロイ
A: App Runner
理由: CI/CD統合、API特化、自動デプロイ

Q: Docker Compose利用、複数コンテナ連携
A: Fargate (ECS)
理由: タスク定義で複数コンテナ、サービス間通信
```

### 頻出シナリオ問題

#### シナリオ1: REST APIデプロイ

```
要件:
- Node.js REST API
- GitHubからデプロイ
- 自動スケーリング
- インフラ管理最小化
- 予算制約あり

解答: App Runner

理由:
✓ Node.jsネイティブサポート
✓ GitHub直接連携
✓ 自動スケーリング標準
✓ フルマネージド
✓ 従量課金、低コスト

設定:
- ソース: GitHub
- ランタイム: Node.js 16
- 自動デプロイ: 有効
- 最小: 1, 最大: 10
- 0.5 vCPU, 1 GB
```

#### シナリオ2: データベース接続API

```
要件:
- Python API
- VPC内RDS接続
- セキュアアクセス
- CI/CD統合

解答: App Runner + VPC Connector

理由:
✓ VPC Connector経由でRDS接続
✓ プライベートサブネット配置
✓ セキュリティグループ制御
✓ 自動デプロイ

構成:
App Runner (VPC Connector)
  ↓
Private Subnet
  ↓
RDS (セキュリティグループ制限)

設定:
- VPC Connector作成
- セキュリティグループ: RDS 3306ポート許可
- IAMロール: Secrets Manager読み取り
```

#### シナリオ3: マイクロサービス展開

```
要件:
- 複数マイクロサービス
- 独立デプロイ
- サービス間通信（内部）
- 個別スケーリング

解答: App Runner（複数サービス） + Internal ALB

理由:
✓ サービス独立デプロイ
✓ 個別スケーリング設定
✓ VPC Connector経由内部通信
✓ 管理簡素化

構成:
App Runner (Frontend)
  ↓ VPC Connector
Internal ALB
  ↓
App Runner (Backend Services)
  ├─ Service A
  ├─ Service B
  └─ Service C

代替案: Fargate
理由: より複雑な構成、ECSサービス連携必要な場合
```

#### シナリオ4: バッチ処理

```
要件:
- データ処理バッチ
- 実行時間3時間
- スケジュール実行
- コスト最小化

解答: Fargate + EventBridge

理由:
× App Runner: 120秒制限超過
✓ Fargate: 長時間実行可能
✓ EventBridge: スケジュール実行
✓ Fargate Spot: コスト削減

ポイント:
- App Runnerは不適切（時間制限）
- Lambda も不適切（15分制限）
- Fargateが最適解
```

#### シナリオ5: コスト最適化

```
要件:
- 小規模API
- トラフィック変動大
- 夜間ほぼアクセスなし
- コスト最小化

解答: App Runner（最小1）

理由:
✓ 自動スケーリング
✓ 最小1インスタンス
✓ トラフィックなし時も課金
✓ リクエスト単位課金

設定:
- 最小: 1（常時稼働）
- 最大: 10
- 0.25 vCPU, 0.5 GB

月額コスト例:
- コンピューティング: 730h × $0.0074 = $5.40
- リクエスト: 100万/月 × $0.10/100万 = $0.10
- 合計: 約$5.50/月

代替案: Lambda
理由: 完全従量課金、アイドル時課金なし
条件: コールドスタート許容可能な場合
```

### App Runner特有の重要ポイント

```yaml
1. デプロイソース:
   ソースコード:
     - GitHub連携
     - 自動ビルド
     - ランタイム限定（Python, Node.js, Java等）
   
   コンテナイメージ:
     - ECR連携
     - カスタムランタイム
     - より柔軟

2. スケーリング:
   自動スケーリング:
     - 同時実行数ベース
     - デフォルト: 100リクエスト/インスタンス
     - 設定簡単
   
   手動スケーリング不可:
     - 最小/最大インスタンス数のみ設定

3. ネットワーク:
   デフォルト:
     - パブリックエンドポイント
     - HTTPS標準
   
   VPC Connector:
     - VPCリソースアクセス
     - プライベートサブネット
     - 追加料金
   
   制約:
     - インバウンドはインターネットのみ
     - Private Link非対応

4. 制限事項:
   タイムアウト:
     - リクエスト: 最大120秒
     - これを超える処理は不適
   
   ストレージ:
     - 永続ストレージなし
     - S3/RDS/DynamoDB使用
   
   ポート:
     - 単一ポート（8080等）
```

### よくある間違い

```yaml
× 誤り: App Runnerでバッチ処理（3時間実行）
○ 正解: Fargate使用（長時間実行可能）
理由: App Runnerは120秒制限

× 誤り: App Runnerで永続データ保存
○ 正解: S3/RDS/DynamoDB使用
理由: App Runnerにローカル永続ストレージなし

× 誤り: VPC内部からのみアクセス（Private Link）
○ 正解: ALB経由、またはFargate使用
理由: App Runnerはパブリックエンドポイントのみ

× 誤り: 複数コンテナ連携（サイドカー）
○ 正解: Fargate (ECS)使用
理由: App Runnerは単一コンテナのみ

× 誤り: 既存ECSクラスター統合
○ 正解: Fargate使用
理由: App RunnerはECS独立
```

### 頻出問題パターン整理

```yaml
Pattern 1: シンプルなWebアプリ/API
キーワード: 迅速、簡単、インフラ管理不要、CI/CD
→ App Runner

Pattern 2: 長時間実行タスク
キーワード: バッチ、2時間以上、スケジュール実行
→ Fargate（App Runnerは120秒制限）

Pattern 3: 既存コンテナ環境統合
キーワード: ECS、EKS、既存クラスター
→ Fargate（App Runner独立）

Pattern 4: プライベートアクセスのみ
キーワード: VPC内部のみ、Private Link
→ Fargate（App Runnerパブリック）

Pattern 5: コスト最適化（変動トラフィック）
キーワード: トラフィック変動大、アイドル時間多い
→ Lambda or App Runner（最小1）

Pattern 6: マイクロサービス迅速構築
キーワード: マイクロサービス、独立デプロイ、簡単
→ App Runner（各サービス独立）

Pattern 7: 複雑なネットワーク要件
キーワード: 複数VPC、Transit Gateway、複雑ルーティング
→ Fargate（より柔軟なVPC統合）
```

### まとめ

**試験で重要なポイント:**

- **サービス選択**: App Runner vs Fargate vs Lambda vs Beanstalk
- **制約理解**: 120秒制限、永続ストレージなし、パブリックエンドポイント
- **適用判断**: WebアプリAPI、迅速デプロイ、インフラ管理最小化
- **VPC統合**: VPC Connector使用、プライベートリソースアクセス
- **CI/CD**: GitHub/ECR自動デプロイ

**判断基準:**

- Webアプリ/API + インフラ管理最小化 → **App Runner**
- 長時間実行 + コンテナ → **Fargate**
- イベント駆動 + 短時間実行 → **Lambda**
- レガシーアプリ + プラットフォーム管理 → **Elastic Beanstalk**
