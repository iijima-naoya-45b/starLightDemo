## SAA（ソリューションアーキテクト アソシエイト）

### 頻出ポイント

#### 1. SageMaker基本概念

```yaml
出題パターン:
  「機械学習モデルを構築・デプロイしたい」

正解アプローチ:
  - Amazon SageMaker使用
  - Studio で開発
  - Training Job でトレーニング
  - Endpoint でデプロイ
  - Model Monitor で監視

キーワード:
  ✅ 完全マネージドML → SageMaker
  ✅ AutoML → SageMaker Autopilot
  ✅ リアルタイム推論 → SageMaker Endpoint
  ✅ バッチ推論 → Batch Transform
```

#### 2. 推論オプション選択

```yaml
シナリオ別選択:

リアルタイム推論:
  要件:
    - 低レイテンシ（< 100ms）
    - 同期レスポンス
    - 常時可用性
  
  ソリューション:
    - SageMaker Real-time Endpoint
    - Auto Scaling
    - Multi-AZ配置

サーバーレス推論:
  要件:
    - 断続的なトラフィック
    - コスト最適化
    - 自動スケーリング
  
  ソリューション:
    - SageMaker Serverless Inference
    - オンデマンド
    - 従量課金

バッチ推論:
  要件:
    - 大量データ処理
    - レイテンシ許容
    - コスト重視
  
  ソリューション:
    - SageMaker Batch Transform
    - S3入出力
    - 実行時間のみ課金
```

#### 3. トレーニング最適化

```yaml
問題:
  「トレーニングコストを削減したい」

回答:
  スポットインスタンス:
    - 最大90%コスト削減
    - マネージドスポットトレーニング
    - チェックポイント自動保存
    - 中断時自動再開

設定:
  use_spot_instances: true
  max_wait_time: 86400
  checkpoint_s3_uri: s3://bucket/checkpoints/
```

#### 4. Feature Store

```yaml
シナリオ:
  「トレーニングと推論で特徴量の一貫性を保ちたい」

正解:
  SageMaker Feature Store:
    オンラインストア:
      - リアルタイム推論用
      - 低レイテンシ
      - ミリ秒レスポンス
    
    オフラインストア:
      - トレーニング用
      - S3ベース
      - バッチアクセス

メリット:
  - 特徴量再利用
  - トレーニング/推論の一貫性
  - バージョン管理
  - チーム間共有
```

#### 3. 大規模リアルタイム推論システム

```yaml

  「1日10億リクエスト、レイテンシ < 50ms」

アーキテクチャ:

      - キャッシング（静的結果）

      ↓
    
    API Gateway:
      - REST API
      - 認証・認可（Cognito/IAM）
      - レート制限
      - リクエスト検証
      ↓
    
    Lambda（前処理）:
      - 入力検証
      - Feature Store取得
      - データ変換
      - 並列化
      ↓
  
  推論層:
    Application Load Balancer:
      - 複数AZ分散
      - ヘルスチェック
      - スティッキーセッション
      ↓
    
    SageMaker Multi-Model Endpoints:
      複数リージョン:
        - ap-northeast-1（Primary）
        - us-west-2（DR）
      
      各リージョン:
        - Multi-AZ配置（3 AZ）
```

## よくある間違い

### 間違い 1: サービス選択の誤り

```yaml
❌ 誤り:
  「画像分析にEMR使用」

✅ 正解:
  画像分類・物体検出:
    - SageMaker（組み込みアルゴリズム）
    - リアルタイム推論
    - Auto Scaling
  
  EMR適用:
    - 大規模データ前処理
    - Spark ETL
    - データエンジニアリング
  
  使い分け:
    データ前処理: EMR / Glue
    モデル開発: SageMaker
    推論: SageMaker
```

### 間違い 2: 推論オプションの誤解

```yaml
❌ 誤り:
  「全ての推論にリアルタイムエンドポイント」

✅ 正解:
  リアルタイムエンドポイント:
    - 低レイテンシ必須
    - 同期レスポンス
    - 常時稼働
    - コスト高
  
  サーバーレス推論:
    - 断続的トラフィック
    - コスト最適化
    - 自動スケーリング
  
  バッチ変換:
    - 大量データ
    - レイテンシ許容
    - コスト削減（70%）
  
  選択基準:
    - レイテンシ要件
    - トラフィックパターン
    - コスト制約
```

### 間違い 3: Feature Store不要論

```yaml
❌ 誤り:
  「Feature Storeは常に不要」

✅ 正解:
  Feature Store必要:
    - 特徴量再利用
    - チーム間共有
    - トレーニング/推論の一貫性
    - バージョン管理
    - 系譜追跡
  
  Feature Store不要:
    - シンプルなモデル
    - 単一プロジェクト
    - 特徴量少ない
  
  エンタープライズ:
    - ほぼ必須
    - MLOps基盤
    - ガバナンス
```

### 間違い 4: Auto Scalingの誤解

```yaml
❌ 誤り:
  「Auto Scalingで最小インスタンス数0」

✅ 正解:
  最小インスタンス数:
    高可用性:
      - 最小: 2（Multi-AZ）
      - ヘルスチェック
      - フェイルオーバー
    
    開発環境:
      - 最小: 1（コスト削減）
      - 低可用性許容
    
    コスト重視:
      - サーバーレス推論使用
      - 完全従量課金
      - 最小インスタンス不要
```

### 間違い 5: SageMaker vs Lambda

```yaml
❌ 誤り:
  「全ての推論をLambda実装」

✅ 正解:
  SageMaker推論:
    - 複雑なMLモデル
    - GPU必要
    - 大規模推論
    - モデル管理必要
  
  Lambda推論:
    - 軽量モデル
    - シンプルロジック
    - イベント駆動
    - 15分以内処理
  
  使い分け:
    軽量推論:
      - Scikit-learn（小）
      - ルールベース
      → Lambda
    
    本格ML:
      - Deep Learning
      - 大規模モデル
      - GPU推論
      → SageMaker
```

## サービス比較（重要）

### SageMaker vs EMR vs Glue

```yaml
データ前処理:
  Glue:
    - サーバーレスETL
    - 小〜中規模
    - シンプル変換
    - コスト効率
  
  EMR:
    - 大規模処理
    - Spark/Hadoop
    - カスタマイズ可能
    - 継続的処理

モデル開発:
  SageMaker:
    - ML専用
    - マネージド環境
    - AutoML
    - モデルデプロイ
  
  EMR:
    - Spark MLlib
    - カスタム実装
    - データエンジニアリング

推論:
  SageMaker:
    - リアルタイム
    - バッチ
    - サーバーレス
    - モデル管理
  
  Lambda:
    - 軽量推論
    - イベント駆動
    - サーバーレス

典型的なパイプライン:
  Glue/EMR（データ前処理）
    ↓
  SageMaker（トレーニング）
    ↓
  SageMaker（推論）
```
