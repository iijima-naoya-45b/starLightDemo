## EFS 試験Tips (SAA/SAP)

### 頻出トピック

#### 1. EFS vs EBS vs S3 選択

```yaml
頻出問題パターン:

Q: 複数EC2インスタンスから同時アクセス必要
A: EFS（NFSファイルシステム）

Q: 単一EC2専用、高IOPS必要
A: EBS（ブロックストレージ）

Q: 静的コンテンツ配信、無制限スケール
A: S3（オブジェクトストレージ）

Q: WordPressなどCMS、複数サーバーで画像共有
A: EFS（共有ファイルシステム）

Q: データベースボリューム、1インスタンス専用
A: EBS（低レイテンシー）
```

**選択基準マトリクス:**

| 要件 | 推奨 | 理由 |
|---|---|---|
| 複数インスタンス同時アクセス | **EFS** | NFSプロトコル |
| 単一インスタンス専用 | **EBS** | 低レイテンシー |
| WebサーバーでCMS | **EFS** | 画像・ファイル共有 |
| データベース | **EBS** | 高IOPS |
| バックアップ・アーカイブ | **S3** | 低コスト |
| コンテナ永続ストレージ | **EFS** | 共有・柔軟性 |

#### 2. ストレージクラスとコスト最適化

```yaml
頻出問題:

Q: 低頻度アクセス、コスト削減したい
A: EFS Standard-IA + ライフサイクル管理

Q: 開発・テスト環境、単一AZで十分
A: EFS One Zone

Q: 最小コスト、非クリティカル、低頻度アクセス
A: EFS One Zone-IA

Q: 本番環境、高可用性必要
A: EFS Standard（マルチAZ）

自動階層化設定:
  ベストプラクティス:
    - 30日間アクセスなし → IA移行
    - アクセス時自動的にStandardに戻る
    - 最大92%コスト削減
```

**コスト比較:**

| クラス | 月額（100GB） | 可用性 | 用途 |
|---|---|---|---|
| Standard | $30 | 99.99% | 本番アクティブ |
| Standard-IA | $1.9 | 99.99% | 本番低頻度 |
| One Zone | $19 | 99.9% | 開発・テスト |
| One Zone-IA | $1.2 | 99.9% | 非クリティカル |

#### 3. パフォーマンスモード

```yaml
General Purpose vs Max I/O:

Q: 通常のWebアプリケーション
A: General Purpose（デフォルト、低レイテンシー）

Q: ビッグデータ分析、数千の同時接続
A: Max I/O（高スループット、並列処理）

Q: どちらか不明
A: General Purpose（後から変更不可のため安全策）

重要ポイント:
  - 作成後変更不可
  - 迷ったらGeneral Purpose
  - CloudWatchでPercentIOLimit監視
  - 100%に達する場合Max I/O検討
```

#### 4. スループットモード

```yaml
Bursting vs Provisioned vs Elastic:

Q: 小容量（<1TB）で高スループット必要
A: Provisioned Throughput

Q: シンプルな設定、自動スケール希望
A: Elastic Throughput（推奨、新規デフォルト）

Q: コスト最小、通常ワークロード
A: Bursting（従量課金なし）

Elasticの特徴:
  ✓ 自動スケール（最大3GB/s読取、1GB/s書込）
  ✓ 設定不要
  ✓ 使用量に応じた課金
  ✓ 2024年以降の推奨
```

### 頻出シナリオ問題

#### シナリオ1: WordPress on AWS

```
要件:
- WordPressサイト
- Auto Scalingで複数EC2
- 画像・メディアファイル共有
- 高可用性必要

解答:
アーキテクチャ:
  - ALB: 負荷分散
  - EC2 Auto Scaling: Webサーバー
  - EFS Standard: 画像・ファイル共有（マルチAZ）
  - RDS Multi-AZ: データベース
  - S3 + CloudFront: 静的コンテンツ配信（オプション）

EFS設定:
  - ストレージクラス: Standard（本番）
  - パフォーマンスモード: General Purpose
  - スループットモード: Elastic
  - ライフサイクル: 30日→Standard-IA
  - 暗号化: 有効

ポイント:
✓ EFS: 複数EC2から画像共有
✓ マルチAZ: 高可用性
✓ ライフサイクル: コスト最適化
```

#### シナリオ4: 機械学習環境

```
要件:
- SageMakerトレーニング
- 大量トレーニングデータ（5TB）
- 複数ジョブ並列実行
- チェックポイント保存

解答:
構成:
  - SageMaker: トレーニングジョブ
  - EFS: データ共有
  - S3: 元データ保存・結果保存

EFS設定:
  - ストレージクラス: Standard
  - パフォーマンスモード: General Purpose
  - スループットモード: Elastic or Provisioned
  - サイズ: 自動拡張

ワークフロー:
  1. S3 → EFS: 初回データロード
  2. 複数ジョブがEFS読み取り
  3. チェックポイント → EFS保存
  4. 最終結果 → S3保存

メリット:
✓ 複数ジョブでデータ共有
✓ S3より高速読み取り
✓ チェックポイント保存容易
```

### セキュリティ頻出ポイント

```yaml
暗号化:
  Q: 保管時の暗号化をどう実現？
  A: ファイルシステム作成時に暗号化有効化（AWS KMS）
  
  Q: 転送時の暗号化は？
  A: amazon-efs-utils + TLSオプション

  重要: 作成後に暗号化追加不可

アクセス制御:
  レイヤー1: セキュリティグループ（NFS port 2049）
  レイヤー2: IAMポリシー（API操作制御）
  レイヤー3: ファイルシステムポリシー（リソースベース）
  レイヤー4: POSIX権限（ファイルレベル）

アクセスポイント:
  ユースケース:
    - マルチテナント環境
    - ユーザー別分離
    - アプリケーション別制御
  
  設定:
    - UID/GID強制
    - ルートディレクトリ指定
    - IAM認証統合
```

### パフォーマンス頻出ポイント

```yaml
スループット制限:

Burstingモード:
  - 計算: 50 MB/s per TB（ベースライン）
  - バースト: 100 MB/s
  - 問題: 小容量で高スループット必要な場合
  - 解決: Provisioned or Elastic

Elasticモード:
  - 自動スケール
  - 最大3GB/s読取、1GB/s書込
  - 推奨される選択肢

監視:
  - BurstCreditBalance: クレジット残高
  - PercentIOLimit: IO制限使用率（>100%でMax I/O検討）
  - ClientConnections: 接続数
```

### よくある間違い

```yaml
× 誤り: EBSを複数EC2にマウント（通常のEBS）
○ 正解: EFSを複数EC2にマウント
  補足: EBS io2 Multi-Attachは最大16インスタンス（特殊用途）

× 誤り: EFS作成後に暗号化有効化
○ 正解: 作成時に暗号化指定（後から変更不可）

× 誤り: パフォーマンスモード後から変更
○ 正解: 作成時に決定（変更不可、再作成必要）

× 誤り: セキュリティグループ設定せずマウント
○ 正解: NFS（2049）ポート許可必須

× 誤り: 全データStandard保存
○ 正解: ライフサイクル管理で自動IA移行
```

### まとめ

**試験対策の重要ポイント:**

1. **選択基準理解:**
   - 複数インスタンス同時アクセス → EFS
   - 単一インスタンス専用 → EBS
   - オブジェクトストレージ → S3

2. **コスト最適化:**
   - ライフサイクル管理（30日推奨）
   - 本番: Standard、非本番: One Zone

3. **パフォーマンス:**
   - General Purpose（デフォルト）
   - Max I/O（高並列のみ）
   - Elastic Throughput（推奨）

4. **セキュリティ:**
   - 暗号化: 作成時設定
   - セキュリティグループ: NFS 2049
   - マルチレイヤー制御

5. **ユースケース:**
   - CMS（WordPress）
   - コンテナ永続ストレージ
   - 機械学習トレーニング
   - ハイブリッドクラウド
