## Direct Connect 試験Tips (SAA/SAP)

AWS Solutions Architect Associate/Professional試験での Direct Connect 頻出問題と対策を解説します。

### 頻出トピック

#### 1. Direct Connect vs VPN

**必須理解ポイント:**

```yaml
Direct Connect:
  接続方式: 専用プライベート接続
  帯域幅: 50Mbps 〜 100Gbps
  レイテンシー: 低・一貫性あり
  導入期間: 数週間〜数ヶ月
  コスト: 高 (固定費 + 従量)
  暗号化: オプション (MACsec)
  用途:
    - 大容量データ転送
    - 低レイテンシー要求
    - 安定した帯域幅必要
    - 長期利用

Site-to-Site VPN:
  接続方式: インターネット経由
  帯域幅: 最大1.25Gbps/tunnel
  レイテンシー: 変動あり
  導入期間: 数分〜数時間
  コスト: 低 ($0.05/時間)
  暗号化: IPsec (標準)
  用途:
    - 小容量データ転送
    - 短期プロジェクト
    - バックアップ回線
    - 即座の接続必要
```

**頻出問題パターン:**

```
Q1: オンプレミスから月間50TBのデータをS3に転送する必要がある。
    最もコスト効率的な方法は？

A: Direct Connect + Public VIF
   理由:
   - 大容量転送でコスト削減効果大
   - 転送時間の予測可能性
   - インターネット帯域への影響なし
   
   コスト試算:
   - Direct Connect (1Gbps): $205/月
   - データ転送: 50TB × $0.0514 = $2,570
   - 合計: 約$2,775/月
   
   × VPN: 帯域制限、転送時間長い
   × インターネット: 高額、不安定

Q2: 低レイテンシー(<10ms)が必要なハイブリッドクラウド環境を構築したい。

A: Direct Connect + Private VIF
   理由:
   - 専用線で安定した低レイテンシー
   - VPN: インターネット経由でレイテンシー変動大
   
   レイテンシー目安:
   - Direct Connect: 2-5ms (東京リージョン)
   - VPN: 20-100ms (インターネット依存)
```

#### 2. Virtual Interface (VIF) タイプ

**重要な理解:**

```yaml
Private VIF:
  接続先: VPC (Virtual Private Gateway / Transit Gateway)
  用途: EC2、RDS、内部リソースへのアクセス
  IPアドレス: プライベート
  ルーティング: BGP
  特徴:
    - VPC内リソースへの接続
    - RFC1918プライベートアドレス
    - 複数VPC接続可能 (Direct Connect Gateway経由)

Public VIF:
  接続先: AWS公開サービス
  用途: S3、DynamoDB、CloudFront、EC2 API等
  IPアドレス: パブリック
  ルーティング: BGP (パブリックIPプレフィックス広告)
  特徴:
    - パブリックエンドポイントへの接続
    - インターネット経由不要
    - NAT不要

Transit VIF:
  接続先: Transit Gateway
  用途: 複数VPC/VPN統合管理
  特徴:
    - 最新の推奨構成
    - 複数VPC一元管理
    - 最大3つのTransit Gateway接続
    - Jumbo Frame (MTU 8500) 対応
```

**頻出問題:**

```
Q: オンプレミスから複数リージョンの複数VPCへ接続したい。
   最もスケーラブルな方法は？

A: Direct Connect + Direct Connect Gateway + Private VIF
   構成:
   オンプレミス
     ↓ Direct Connect
   Direct Connect Gateway
     ↓
   ├─ VGW (VPC-Tokyo-1)
   ├─ VGW (VPC-Tokyo-2)
   ├─ VGW (VPC-US-1)
   └─ VGW (VPC-EU-1)
   
   メリット:
   - 単一Direct Connect で複数リージョンアクセス
   - 最大10個のVGW接続可能
   - リージョン追加が容易
   
   × 誤答: 各VPCに個別のDirect Connect
   × 誤答: Public VIF (VPC内リソースアクセス不可)

Q: S3への大容量データ転送をNAT Gateway経由せずに実現したい。

A: Direct Connect + Public VIF
   理由:
   - S3のパブリックエンドポイントへ直接アクセス
   - NAT Gateway不要 → コスト削減
   - インターネット経由不要
   
   × 誤答: Private VIF + VPC Endpoint
     (Direct Connect から VPC Endpoint は非効率)
```

#### 3. 冗長化構成

**必須パターン:**

```yaml
レベル1: 単一Direct Connect (非推奨):
  構成: 1接続のみ
  可用性: 低 (単一障害点)
  用途: 開発環境のみ
  コスト: 低

レベル2: Direct Connect + VPN (推奨):
  構成:
    - Primary: Direct Connect
    - Backup: Site-to-Site VPN
  可用性: 中
  フェイルオーバー: 自動 (BGP)
  用途: 中小規模本番環境
  コスト: 中

レベル3: 同一ロケーション冗長:
  構成: 同じDirect Connect Locationに2接続
  可用性: 中〜高
  対策: デバイス障害
  リスク: ロケーション障害
  コスト: 中

レベル4: マルチロケーション冗長 (AWS推奨):
  構成: 異なる2つのDirect Connect Locationに接続
  可用性: 最高 (99.99%+)
  対策: ロケーション障害、デバイス障害
  用途: エンタープライズ本番環境
  コスト: 高
```

**頻出問題:**

```
Q: 99.99%の可用性が必要なミッションクリティカルなアプリケーション。
   Direct Connect接続の推奨構成は？

A: マルチロケーション冗長構成
   構成:
   オンプレミス
     ├─ Direct Connect Location A (2接続)
     └─ Direct Connect Location B (2接続)
   合計4接続
   
   理由:
   - ロケーション全体の障害に対応
   - 各ロケーション内でも冗長
   - SLA 99.99%達成可能
   
   追加対策:
   - Site-to-Site VPN (バックアップ)
   - BGPで優先度制御
   - CloudWatch監視
   
   × 誤答: 単一ロケーション (ロケーション障害に脆弱)
   × 誤答: VPNのみ (帯域・レイテンシー要件満たさず)

Q: コストを抑えつつ冗長性も確保したい。

A: Direct Connect + Site-to-Site VPN
   構成:
   - Primary: Direct Connect (1Gbps)
   - Backup: VPN (自動フェイルオーバー)
   
   BGP設定:
   - Direct Connect: Local Preference 200
   - VPN: Local Preference 100
   
   メリット:
   - コスト効率的
   - 自動フェイルオーバー
   - VPNは数分で構築可能
   
   コスト (月額):
   - Direct Connect: $205
   - VPN: $36
   - 合計: $241 + データ転送料
```

#### 4. LAG (Link Aggregation Group)

**重要ポイント:**

```yaml
LAG概要:
  - 複数の物理接続を論理的に束ねる
  - LACP (IEEE 802.1AX-2008)
  - 最大4接続まで集約

制約:
  - 全て同じ帯域幅必須
  - 同じDirect Connect Location必須
  - Active/Active構成

メリット:
  - 帯域幅拡張 (4 × 10Gbps = 40Gbps)
  - 運用簡素化 (単一論理接続)
  - 冗長性向上

設定:
  - 最小リンク数指定可能
  - リンク障害時の挙動定義
```

**頻出問題:**

```
Q: 現在1Gbpsの接続で帯域不足。4Gbpsに拡張したい。
   ダウンタイムを最小化する方法は？

A: LAG (Link Aggregation Group)
   手順:
   1. LAG作成 (4 × 1Gbps)
   2. 新規接続追加 (3接続)
   3. 既存接続をLAGに追加
   4. トラフィック分散確認
   
   メリット:
   - 段階的な追加でダウンタイム最小
   - Active/Active負荷分散
   - 単一論理接続で管理容易
   
   × 誤答: 既存接続を削除して10Gbps接続
     (長時間のダウンタイム発生)

Q: LAGで2つの接続のうち1つが故障した場合の挙動は？

A: 自動的に残りの接続で継続
   - LACP が故障を検知
   - トラフィックを正常な接続に再分配
   - 最小リンク数を下回ると全体ダウン
   
   ベストプラクティス:
   - 最小リンク数 = 接続数 - 1
   - 例: 4接続の場合、最小リンク数=3
   - 1接続故障でも稼働継続
```

#### 5. Direct Connect Gateway

**重要な理解:**

```yaml
機能:
  - 複数リージョンのVPC接続
  - グローバルリソース
  - Private/Transit VIF対応

制限:
  - Virtual Private Gateway: 最大10
  - Transit Gateway: 最大3
  - VIF per Gateway: 最大30

注意点:
  - VPC間通信は不可 (VPC Peering必要)
  - リージョン間はAWS Backboneを経由
  - 同じDirect Connect Gatewayに接続したVPC間は
    Direct Connect Gateway経由で通信不可
```

**頻出問題:**

```
Q: 単一のDirect Connect接続から東京、バージニア、シンガポールの
   VPCへ接続したい。

A: Direct Connect Gateway
   構成:
   オンプレミス (東京)
     ↓ Direct Connect (東京ロケーション)
   Direct Connect Gateway (グローバル)
     ↓
   ├─ VPC (ap-northeast-1)
   ├─ VPC (us-east-1)
   └─ VPC (ap-southeast-1)
   
   メリット:
   - 単一接続で複数リージョンアクセス
   - AWS Backboneで高速転送
   - スケーラブル
   
   注意:
   - レイテンシーは物理距離に依存
   - VPC間通信はVPC Peering必要

Q: Direct Connect Gateway接続した3つのVPC間で通信したい。

A: VPC Peering または Transit Gateway
   理由:
   - Direct Connect Gatewayは「オンプレミス→AWS」のみ
   - VPC間通信は別途設定必要
   
   オプション1: VPC Peering
   - VPC-A ↔ VPC-B
   - VPC-B ↔ VPC-C
   - VPC-A ↔ VPC-C
   
   オプション2: Transit Gateway (推奨)
   - 中央ハブで一元管理
   - スケーラブル
   
   × 誤答: Direct Connect Gateway経由で通信可能
```

#### 6. Transit Gateway + Direct Connect

**重要パターン:**

```yaml
構成:
  オンプレミス
    ↓ Transit VIF
  Transit Gateway
    ↓
  ├─ 複数VPC (最大5,000)
  ├─ Site-to-Site VPN
  └─ VPC Peering

メリット:
  - 中央集約管理
  - 複数VPC/VPN統合
  - ルーティング制御容易
  - 大規模環境に最適

コスト:
  - Transit Gateway: $0.05/時間/アタッチメント
  - データ転送: $0.02/GB
```

**頻出問題:**

```
Q: 20個のVPCとオンプレミスを接続。将来50個に拡張予定。

A: Transit Gateway + Direct Connect (Transit VIF)
   理由:
   - スケーラブル (最大5,000 VPC)
   - 中央管理で運用容易
   - VPC追加が簡単
   - ルートテーブルで柔軟な制御
   
   × 誤答: 各VPCにPrivate VIF
     (管理複雑、スケールしない)
   × 誤答: Direct Connect Gateway + VGW
     (最大10 VGW まで)

Q: 本番VPCと開発VPCを分離したいが、どちらもオンプレミスから
   アクセス可能にしたい。

A: Transit Gateway のルートテーブル分離
   構成:
   Transit Gateway
     ├─ Production Route Table
     │   ├─ VPC-Prod-1
     │   ├─ VPC-Prod-2
     │   └─ Route to オンプレミス
     │
     └─ Development Route Table
         ├─ VPC-Dev-1
         ├─ VPC-Dev-2
         └─ Route to オンプレミス
   
   設定:
   - 本番VPCと開発VPC間は通信不可
   - 各VPCはオンプレミスと通信可能
   - セキュリティ境界明確
```

### 頻出シナリオ問題

#### シナリオ1: 大規模データ移行

```
要件:
- オンプレミスのデータセンターからAWSへ200TBのデータ移行
- 移行期間: 1ヶ月以内
- 移行中も既存システムは稼働継続
- コスト意識

解答パターン:

オプション1: Direct Connect (10Gbps)
  移行時間: 約2週間 (実効8Gbps想定)
  コスト: 
    - Direct Connect: $1,620/月
    - データ転送 (イン): 無料
    - 合計: $1,620
  
  メリット:
    - 高速転送
    - 既存業務への影響最小
    - 移行後も継続利用可能
  
  デメリット:
    - 導入に数週間必要
    - 短期利用には高コスト

オプション2: AWS Snowball Edge
  移行時間: 2-3週間 (輸送含む)
  コスト:
    - デバイス料金: $250/device × 4
    - 合計: $1,000
  
  メリット:
    - 短期間で完了
    - コスト効率的
  
  デメリット:
    - 物理的な輸送必要
    - 移行後の恒久的接続にならない

オプション3: ハイブリッド (推奨)
  - 初期: Snowball Edge (100TB)
  - 残り: Direct Connect (100TB + 継続利用)
  
  メリット:
    - 迅速な初期移行
    - 継続的な接続確保
    - バランスの取れたコスト

試験での選択ポイント:
- 「継続利用」明記 → Direct Connect
- 「1回限り」明記 → Snowball
- 「即座に」明記 → VPN or Snowball
```

#### シナリオ2: 高可用性ハイブリッドクラウド

```
要件:
- オンプレミスとAWSの統合
- SLA 99.99%必須
- RTO 5分以内
- RPO 1分以内
- 予算考慮

解答:

推奨構成:
  オンプレミス
    ├─ ロケーションA: Direct Connect (1Gbps)
    └─ ロケーションB: Direct Connect (1Gbps)
  
  AWS
    ├─ Transit Gateway
    └─ Site-to-Site VPN (バックアップ)

設定:
  1. BGP優先度:
     - Direct Connect Location A: Weight 200
     - Direct Connect Location B: Weight 200

  2. ヘルスチェック:
     - CloudWatch + Lambda
     - BGPセッション監視
     - 自動フェイルオーバー
  
  3. データレプリケーション:
     - データベース: 同期レプリケーション
     - ファイル: AWS DataSync

コスト (月額):
  - Direct Connect × 2: $410
  - Transit Gateway: $72 (2アタッチメント)
  - VPN: $36
  - 合計: 約$518 + データ転送料

可用性計算:
  - 各Direct Connect: 99.9%
  - 2つの独立接続: 1 - (0.001 × 0.001) = 99.9999%
  - VPNバックアップ追加: さらに向上
  - 目標 99.99% 達成

SAP試験でのポイント:
- マルチロケーション冗長
- 自動フェイルオーバー設計
- 段階的な障害対応
- コスト最適化の説明
```

### よくある間違い

#### 1. VIFタイプの混同

```
× 誤り: Private VIFでS3にアクセス
○ 正解: Public VIFまたはPrivate VIF + VPC Endpoint

× 誤り: Public VIFでEC2インスタンスにアクセス
○ 正解: Private VIF使用

× 誤り: Transit VIFをVirtual Private Gatewayに接続
○ 正解: Transit VIFはTransit Gatewayのみ
```

#### 2. 冗長化の理解不足

```
× 誤り: 単一Direct Connect で本番環境
○ 正解: 最低でもDirect Connect + VPN

× 誤り: 同じルーター、同じポート経由
○ 正解: 異なるデバイス、異なるパス

× 誤り: 冗長化設定したが、BGP優先度未設定
○ 正解: BGP属性で明示的な優先度制御
```

#### 3. コスト理解の誤り

```
× 誤り: Direct Connectはデータ転送無料
○ 正解: インバウンド無料、アウトバウンド課金

× 誤り: VPNの方が常に安い
○ 正解: 大容量転送時はDirect Connectが安い

試算例 (月間50TB転送):
  Direct Connect: $205 + $2,570 = $2,775
  VPN: $36 + 通信キャリア費用 (変動大)
```
