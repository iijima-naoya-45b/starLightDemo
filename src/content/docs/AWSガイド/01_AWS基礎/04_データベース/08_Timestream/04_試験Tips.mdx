## Timestream 試験Tips (SAA/SAP)

### 頻出トピック

#### 1. Timestreamの選択基準

```yaml
Timestreamが最適:
  ✓ 時系列データ（タイムスタンプ必須）
  ✓ 高頻度な書き込み（秒・分単位）
  ✓ IoT、DevOps、テレメトリ
  ✓ 時間範囲クエリが中心
  ✓ リアルタイム分析 + 長期保存

Timestreamが不適:
  ✗ 非時系列データ
  ✗ 複雑なトランザクション
  ✗ 結合が多いクエリ
  ✗ 汎用的なデータベース用途
```

#### 2. 他のデータベースとの使い分け

```yaml
Timestream vs DynamoDB:
  Timestream:
    - 時系列データ専用
    - 時間範囲クエリ最適化
    - 2層ストレージ（自動コスト最適化）
    - 時系列関数内蔵
    - 用途: IoT、監視、テレメトリ
  
  DynamoDB:
    - 汎用NoSQL
    - キーバリューアクセス
    - 単一桁ミリ秒レスポンス
    - トランザクション対応
    - 用途: セッション、カート、汎用アプリ

Timestream vs RDS/Aurora:
  Timestream:
    - 時系列データ専用
    - スキーマレス
    - 無制限スケール
    - 書き込み最適化
    - 用途: 大量センサーデータ
  
  RDS/Aurora:
    - リレーショナル
    - ACID準拠
    - 複雑なクエリ・結合
    - トランザクション
    - 用途: 業務アプリ、ERP

Timestream vs Redshift:
  Timestream:
    - リアルタイム分析
    - 高頻度書き込み
    - メモリストアで高速クエリ
    - 用途: リアルタイム監視
  
  Redshift:
    - ペタバイト級DWH
    - バッチ分析
    - 複雑な集約・結合
    - 用途: ビジネスインテリジェンス

Timestream vs OpenSearch:
  Timestream:
    - 時系列データ専用
    - 数値データ最適化
    - SQL互換
    - 用途: メトリクス、センサーデータ
  
  OpenSearch:
    - 全文検索・ログ分析
    - 非構造化データ
    - リアルタイム検索
    - 用途: ログ検索、セキュリティ分析

Timestream vs CloudWatch Logs Insights:
  Timestream:
    - 構造化時系列データ
    - 長期保存（年単位）
    - 複雑な時系列分析
    - カスタムアプリケーション統合
  
  CloudWatch Logs Insights:
    - ログデータ
    - 短期保存（デフォルト）
    - シンプルなログクエリ
    - AWS監視統合
```

### 頻出シナリオ

#### シナリオ1: IoTセンサーデータ

```
要件:
  - 100万台のセンサー
  - 1分間隔でデータ送信
  - リアルタイム監視ダッシュボード
  - 過去2年分のトレンド分析

解答: Timestream
  ✓ 大量書き込み対応
  ✓ メモリストアでリアルタイム
  ✓ マグネティックストアで長期保存
  ✓ 時系列関数で分析

誤答例:
  ✗ DynamoDB: 時系列クエリ非効率、コスト高
  ✗ RDS: スケール限界、コスト高
  ✗ Redshift: リアルタイム分析に不向き
```

#### シナリオ2: DevOps監視

```
要件:
  - 1000台のEC2インスタンス
  - CPU、メモリ、ネットワークメトリクス
  - 5秒間隔で収集
  - Grafanaでリアルタイム可視化
  - 90日間保持

解答: CloudWatch + Timestream
  CloudWatch: メトリクス収集
  Kinesis Firehose: ストリーミング
  Timestream: 長期保存・分析
  Grafana: 可視化

理由:
  ✓ CloudWatchとの統合
  ✓ 高頻度メトリクス対応
  ✓ コスト効率的な長期保存
  ✓ Grafanaネイティブ対応
```

#### シナリオ3: 産業テレメトリ

```
要件:
  - 工場内1000台の産業機器
  - 振動、温度、稼働状態
  - 予知保全のための機械学習
  - 10年間データ保持（コンプライアンス）

解答: IoT Core → Lambda → Timestream → SageMaker
  IoT Core: デバイス接続
  Lambda: データ変換
  Timestream: 長期保存（10年）
  SageMaker: 予知保全モデル

理由:
  ✓ 長期保存対応
  ✓ SageMaker統合
  ✓ コスト効率的
  ✓ スケーラブル
```

#### シナリオ4: アプリケーションメトリクス

```
要件:
  - マイクロサービスアーキテクチャ
  - API レスポンスタイム、エラーレート
  - リアルタイムアラート
  - 30日間保持

解答: Timestream
  メモリストア: 24時間（リアルタイム監視）
  マグネティックストア: 30日
  Lambda: 異常検知・アラート

理由:
  ✓ 高頻度メトリクス対応
  ✓ リアルタイムクエリ
  ✓ Lambda統合でアラート
```

### データベース選択フローチャート

```yaml
質問1: 時系列データか？
  YES → Timestream候補
  NO → DynamoDB / RDS / その他

質問2: 高頻度な書き込み（秒・分単位）か？
  YES → Timestream
  NO → DynamoDB / RDS

質問3: リアルタイム分析 + 長期保存の両方が必要か？
  YES → Timestream（2層ストレージ）
  NO → 他の選択肢検討

質問4: 時系列関数（移動平均、補間など）が必要か？
  YES → Timestream
  NO → 他の選択肢も可

質問5: コスト最適化が重要か？
  YES → Timestream（自動階層化）
  NO → Aurora / RDS も選択肢
```

### よくある間違い

```yaml
誤り1: ログデータにTimestreamを選択
  ✗ ログ（非構造化）→ Timestream選択
  ✓ ログ → CloudWatch Logs / OpenSearch
  ※ Timestreamは構造化時系列データ向け

誤り2: トランザクション処理にTimestreamを選択
  ✗ EC決済 → Timestream
  ✓ EC決済 → RDS / DynamoDB（トランザクション対応）
  ※ Timestreamは追記型、トランザクション非対応

誤り3: バッチ分析にTimestreamを選択
  ✗ 月次バッチ集計 → Timestream
  ✓ 月次バッチ集計 → Redshift / Athena
  ※ Timestreamはリアルタイム分析向け

誤り4: メモリストア保持期間の設定ミス
  ✗ メモリストア: 365日（コスト高）
  ✓ メモリストア: 数時間〜1日（必要最小限）
  ※ 長期保存はマグネティックストアで

誤り5: DynamoDBとTimestreamの混同
  ✗ セッション管理 → Timestream
  ✓ セッション管理 → DynamoDB（キーバリュー高速）
  ✗ IoTセンサー → DynamoDB（コスト高、非効率）
  ✓ IoTセンサー → Timestream（時系列最適化）
```
