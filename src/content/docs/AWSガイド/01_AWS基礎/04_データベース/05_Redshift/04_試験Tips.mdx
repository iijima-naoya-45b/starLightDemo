## Redshift 試験Tips (SAA/SAP)

### 頻出トピック

#### 1. Redshift vs RDS vs DynamoDB

```yaml
Redshift:
  - データウェアハウス
  - OLAP（分析処理）
  - ペタバイト規模
  - 複雑な集計、JOIN
  - MPP並列処理
  - 列指向ストレージ
  - 用途: BI、データ分析、レポート

RDS:
  - RDBMS
  - OLTP（トランザクション処理）
  - 最大64TB
  - 正規化、ACID
  - 用途: アプリケーションDB

DynamoDB:
  - NoSQL
  - キーバリュー型
  - ミリ秒レスポンス
  - 無制限スケール
  - 用途: セッション、IoT、ゲーム
```

#### 2. Redshift Spectrum の利用

```yaml
特徴:
  - S3データを直接クエリ
  - データロード不要
  - Parquet、ORC、JSON対応
  - Glue Data Catalog連携

用途:
  - 履歴データ（コールドデータ）分析
  - データレイク統合
  - ETL削減
  - ストレージコスト削減

試験ポイント:
  問: 数PBの履歴データをコスト効率的に分析したい
  答: Redshift Spectrum で S3データ直接クエリ
  
  問: データをRedshiftにロードせずに分析したい
  答: Redshift Spectrum 使用
```

#### 3. ノードタイプ選択

```yaml
RA3（推奨）:
  - ストレージとコンピュート分離
  - S3ベースのマネージドストレージ
  - 柔軟なスケーリング
  - 選択: 大半のケース

DC2（レガシー）:
  - SSDベース
  - 高速計算
  - ストレージ制限あり
  - 選択: 小規模、高頻度アクセス
```

#### 4. クエリパフォーマンス最適化

```yaml
分散キー（DISTKEY）:
  - JOIN頻度高い列
  - データ均等分散
  - 試験: JOIN多い列を選択

ソートキー（SORTKEY）:
  - WHERE, ORDER BY, GROUP BY列
  - 範囲クエリ列
  - 試験: フィルタ条件列を選択

圧縮エンコーディング:
  - 自動（COPY時）
  - 最大10倍圧縮
  - ストレージ削減

Materialized Views:
  - 事前計算
  - クエリ高速化
  - 自動リフレッシュ
```

#### 5. データロード方法

```yaml
COPY コマンド（推奨）:
  - S3からロード
  - 並列処理
  - 圧縮対応
  - 最速

INSERT:
  - 小規模データ
  - 低速
  - 非推奨（大規模）

試験ポイント:
  問: 大量データを効率的にロードしたい
  答: COPY コマンドでS3からロード
```

#### 6. バックアップとリカバリ

```yaml
自動スナップショット:
  - 8時間ごとまたは5GB変更ごと
  - 保持期間: 1-35日
  - S3保存
  - 無料（クラスター容量まで）

手動スナップショット:
  - 任意タイミング
  - 削除まで保持
  - 課金対象

クロスリージョンスナップショット:
  - DR対策
  - 自動コピー可能
  
試験ポイント:
  問: DR対策でスナップショットを別リージョンに保存したい
  答: クロスリージョンスナップショットコピー有効化
```

#### 7. セキュリティ

```yaml
暗号化:
  保管時: AES-256（KMS/HSM）
  転送時: SSL/TLS
  クラスター作成時のみ設定
  
ネットワーク:
  - VPC配置
  - プライベートサブネット推奨
  - セキュリティグループ
  
認証:
  - IAM認証
  - データベースユーザー
  - SAML 2.0（SSO）

試験ポイント:
  問: 既存クラスターを暗号化したい
  答: スナップショット作成 → 暗号化有効で復元
```

### シナリオ別選択

#### シナリオ 1: 大規模データ分析

```yaml
要件:
  - 数百TBのデータ分析
  - 複雑な集計クエリ
  - BIツール連携

選択: Redshift
理由:
  - MPP並列処理
  - 列指向ストレージ
  - PostgreSQL互換
```

#### シナリオ 2: S3データレイク分析

```yaml
要件:
  - S3に数PBのログデータ
  - 履歴データ分析
  - コスト最適化

選択: Redshift Spectrum
理由:
  - S3データ直接クエリ
  - データロード不要
  - スキャン量課金
```

#### シナリオ 3: リアルタイムダッシュボード

```yaml
要件:
  - トランザクションDB（RDS）
  - リアルタイムBI
  - 複雑な分析クエリ

選択: RDS → DMS → Redshift → QuickSight
理由:
  - CDC（継続的レプリケーション）
  - 本番DB負荷分離
  - Materialized Views活用
```

#### シナリオ 4: マルチリージョンDR

```yaml
要件:
  - DR対策
  - RPO: 8時間
  - RTO: 数時間

選択: クロスリージョンスナップショットコピー
理由:
  - 自動コピー
  - 低コスト
  - スナップショットから復元
```

### よくある間違い

```yaml
× 誤り: Redshiftでトランザクション処理
○ 正解: RDS/Aurora使用（Redshiftは分析向け）

× 誤り: 小規模データにRedshift
○ 正解: RDS/Aurora（Redshift は TB〜PB規模向け）

× 誤り: リアルタイム更新にRedshift
○ 正解: DynamoDB（Redshiftはバッチ更新向け）

× 誤り: INSERTで大量データロード
○ 正解: COPYコマンド使用

× 誤り: 既存クラスターの暗号化設定変更
○ 正解: スナップショット作成 → 暗号化有効で復元
```

### 試験頻出シナリオ

```yaml
シナリオ: 大規模データ分析基盤構築
  データソース: RDS、S3ログ
  要件: BI、複雑な分析、コスト最適化
  解答:
    1. DMS で RDS → Redshift 継続的レプリケーション
    2. Spectrum で S3ログ直接クエリ
    3. Materialized Views でダッシュボード高速化
    4. QuickSight で可視化

シナリオ: マルチリージョンDR構成
  要件: RPO 8時間、RTO 数時間
  解答:
    1. 自動スナップショット有効化
    2. クロスリージョンスナップショットコピー
    3. セカンダリリージョンで復元テスト

シナリオ: パフォーマンス問題
  症状: クエリ遅い、ディスク容量不足
  解答:
    1. ANALYZE実行（統計更新）
    2. VACUUM実行（削除行回収）
    3. 分散キー、ソートキー見直し
    4. Materialized Views 検討
```
