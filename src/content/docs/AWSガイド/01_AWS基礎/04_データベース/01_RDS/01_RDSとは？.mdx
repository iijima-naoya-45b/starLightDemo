## Amazon RDS (Relational Database Service) とは？

Amazon RDSは、マネージド型リレーショナルデータベースサービスです。データベースの運用管理を自動化し、開発者はアプリケーション開発に集中できます。
この資料は、**理想論ではなく、実務で使える実践的なRDSの運用方法**を解説します。

### なぜRDSが必要か

#### 問題のある構成（EC2上で自前でデータベースを管理）

**問題のある状況:**

```
問題のある構成:
- データベースのインストール・設定が必要
- パッチ適用・バージョンアップを手動で実施
- バックアップの管理が煩雑
- レプリケーションの設定が複雑
- 障害時の復旧作業が手動
- モニタリング・ログ管理の設定が必要
- セキュリティパッチの適用漏れリスク
- スケーリングの実装が困難

影響:
- 運用負荷が高い（DBAが必要）
- 障害復旧に時間がかかる
- セキュリティリスクが高い
- スケーラビリティの欠如
- バックアップ漏れによるデータ損失リスク
```

**解決: RDSによるマネージドデータベース**

```
解決策:
- 自動バックアップ（ポイントインタイムリカバリ）
- 自動パッチ適用
- Multi-AZ配置による高可用性
- リードレプリカによる読み取りスケーリング
- 自動フェイルオーバー（60-120秒）
- 暗号化・監査ログの自動管理

メリット:
- 運用負荷の大幅削減（AWSが管理）
- 高可用性（Multi-AZ自動フェイルオーバー）
- 自動バックアップ（35日間保持可能）
- スケーラビリティ（リードレプリカ）
- セキュリティ（自動パッチ適用、暗号化）
- アプリケーション開発に集中できる
```

### RDSの主要機能

#### 1. 自動バックアップ

```yaml
特徴:
  - 自動日次バックアップ
  - トランザクションログ継続保存
  - ポイントインタイムリカバリ
  - 保持期間: 0-35日

設定:
  バックアップウィンドウ: 深夜推奨
  保持期間: 7日（デフォルト）
  暗号化: KMS
```

#### 2. Multi-AZ配置

```yaml
特徴:
  - 同期レプリケーション
  - 自動フェイルオーバー（60-120秒）
  - AZ障害対応
  - メンテナンス時の高可用性

構成:
  Primary: AZ-1a
  Standby: AZ-1c（同期レプリケーション）
  
フェイルオーバートリガー:
  - AZ障害
  - プライマリDB障害
  - インスタンスクラス変更
  - OSパッチ適用
```

#### 3. Read Replica

```yaml
特徴:
  - 非同期レプリケーション
  - 読み取り負荷分散
  - 最大15個（Aurora: 15個）
  - クロスリージョン対応

用途:
  - レポート生成
  - 分析処理
  - 災害対策

プロモーション:
  - Read ReplicaをPrimaryに昇格可能
  - RPO: 数秒〜数分
```

#### 4. 自動スケーリング

```yaml
Storage Auto Scaling:
  - ストレージ自動拡張
  - ダウンタイムなし
  - 最大容量設定

Compute:
  - インスタンスクラス変更
  - ダウンタイム発生（数分）
```

**コスト最適化のポイント:**
- 開発環境はSingle-AZ
- リザーブドインスタンスで最大72%削減

- Read Replicaで読み取りスケール
- 自動バックアップ保持期間の最適化

### まとめ

**RDSの重要ポイント:**
- マネージド型で運用負荷軽減
- Multi-AZで高可用性
- Read Replicaで読み取りスケール
- 自動バックアップとポイントインタイムリカバリ
- 暗号化によるセキュリティ強化
