## DocumentDB 試験Tips (SAA/SAP)

### 頻出トピック

#### 1. DocumentDB vs DynamoDB vs MongoDB

```yaml
DocumentDB:
  データモデル: ドキュメント（JSON）
  スキーマ: 柔軟（スキーマレス）
  クエリ: MongoDB互換クエリ言語
  スケール: 最大15レプリカ、128TB
  トランザクション: ACID（4.0以降）
  用途: コンテンツ管理、カタログ、複雑なクエリ
  MongoDB互換: API互換
  
DynamoDB:
  データモデル: キーバリュー、ドキュメント
  スキーマ: パーティション/ソートキー必須
  クエリ: キーベースクエリ
  スケール: 無制限
  トランザクション: ACID
  用途: 高スループット、シンプルなクエリ
  レイテンシ: ミリ秒単位

MongoDB（self-managed）:
  全機能: シャーディング、最新機能
  運用負荷: 高い
  管理: 自己管理
```

#### 2. DocumentDB vs RDS

```yaml
DocumentDB:
  データモデル: ドキュメント（JSON）
  スキーマ: 柔軟
  用途: 非構造化・半構造化データ
  スケール: 水平スケール（レプリカ）
  クエリ: MongoDB クエリ言語
  
RDS:
  データモデル: リレーショナル（テーブル）
  スキーマ: 固定
  用途: 構造化データ、ACID要件
  スケール: 垂直スケール、Read Replica
  クエリ: SQL
```

### 頻出シナリオ

#### シナリオ1: MongoDB移行

```
要件: オンプレミスMongoDBをAWSに移行、運用負荷削減
解答: Amazon DocumentDB

ポイント:
✓ MongoDB API互換
✓ フルマネージド
✓ 自動バックアップ・高可用性
✓ AWS DMS で移行可能

注意:
× シャーディング非対応
× 一部集約パイプライン未対応
```

#### シナリオ2: 柔軟なスキーマ要件

```
要件: 製品カタログ、製品タイプごとに異なる属性
解答: Amazon DocumentDB

ポイント:
✓ スキーマレス（柔軟な属性）
✓ ネストしたオブジェクト・配列
✓ JSON ドキュメントモデル
✓ MongoDB クエリ言語

不適切な選択肢:
× RDS: 固定スキーマ、柔軟性低い
```

#### シナリオ3: 高スループットWeb API

```
要件: モバイルアプリバックエンド、数百万リクエスト/秒
解答: Amazon DynamoDB（DocumentDBではない）

ポイント:
✓ DynamoDB: 無制限スケール、ミリ秒レイテンシ
× DocumentDB: レプリカ最大15個まで

DocumentDBが適切なケース:
- 複雑なクエリ・集約処理
- MongoDB互換性必要
- 柔軟なスキーマ
```

#### シナリオ4: コンテンツ管理システム

```
要件: CMS、記事・メディア管理、柔軟なスキーマ、複雑なクエリ
解答: Amazon DocumentDB

ポイント:
✓ 柔軟なドキュメントモデル
✓ ネストした配列・オブジェクト
✓ テキスト検索
✓ アグリゲーションパイプライン
✓ Change Streams でキャッシュ無効化

DocumentDB選択理由:
- 記事タイプごとに異なる属性
- 階層データ（セクション、段落、メディア）
- 複雑な検索クエリ
```

#### シナリオ5: リアルタイムデータ同期

```
要件: モバイルアプリ、リアルタイムデータ同期
解答: DocumentDB + Change Streams + Lambda

構成:
DocumentDB Change Streams → Lambda → AppSync → Mobile App

ポイント:
✓ Change Streams で変更検知
✓ Lambda でイベント処理
✓ AppSync でリアルタイム配信

代替案:
- DynamoDB Streams（よりシンプルなユースケース）
```

#### シナリオ6: IoTデータ収集

```
要件: IoTデバイスデータ、時系列データ、集約クエリ
解答: DocumentDB または Timestream

DocumentDB適切なケース:
✓ 柔軟なメトリクス（デバイスごとに異なる）
✓ 地理空間クエリ
✓ アグリゲーションパイプライン
✓ ドキュメント指向データモデル

Timestream適切なケース:
✓ 純粋な時系列データ
✓ 高速な時系列クエリ
✓ 自動データ階層化
```

### データベース選択フローチャート

```yaml
質問1: データモデルは？
  構造化（テーブル） → RDS
  非構造化（JSON） → 質問2へ

質問2: MongoDB互換性必要？
  はい → DocumentDB
  いいえ → 質問3へ

質問3: スループット要件は？
  数百万リクエスト/秒 → DynamoDB
  数万〜数十万リクエスト/秒 → 質問4へ

質問4: クエリの複雑さは？
  複雑（集約、JOIN） → DocumentDB
  シンプル（キーベース） → DynamoDB

質問5: トランザクション要件は？
  ACIDトランザクション → DocumentDB（4.0以降）、RDS
  結果整合性OK → DynamoDB
```

### DocumentDB vs DynamoDB 使い分け

| 要件 | DocumentDB | DynamoDB |
|---|---|---|
| **MongoDB互換性** | ✓ 必要 | × 不要 |
| **スキーマ柔軟性** | ✓ 高い | △ パーティション/ソートキー必須 |
| **複雑なクエリ** | ✓ 適切 | × 不向き |
| **集約処理** | ✓ アグリゲーションパイプライン | × 制限あり |
| **スループット** | △ 最大15レプリカ | ✓ 無制限 |
| **レイテンシ** | △ ミリ秒（数ms） | ✓ ミリ秒（1桁ms） |
| **スケーラビリティ** | △ 128TB | ✓ 無制限 |
| **トランザクション** | ✓ ACID | ✓ ACID |
| **運用負荷** | ✓ フルマネージド | ✓ フルマネージド |

### 試験でよく出る誤った選択肢

```yaml
× 誤り: 高スループットWeb APIにDocumentDB
○ 正解: DynamoDB（無制限スケール、低レイテンシ）

× 誤り: シンプルなキーバリューアクセスにDocumentDB
○ 正解: DynamoDB（シンプル、低コスト、高速）

× 誤り: MongoDB互換性不要なのにDocumentDB
○ 正解: DynamoDB または RDS（要件に応じて）

× 誤り: DocumentDBのStandbyレプリカで読み取り負荷分散
○ 正解: DocumentDBは全レプリカが読み取り可能（RDSと異なる）

× 誤り: DocumentDBでシャーディング
○ 正解: DocumentDBはシャーディング非対応（レプリカで水平スケール）
```

### SAA試験重要ポイント

```yaml
基本:
  ☐ DocumentDB vs DynamoDB使い分け
  ☐ MongoDB互換性
  ☐ クラスター構成（プライマリ + レプリカ）
  ☐ エンドポイント種類
  ☐ 自動バックアップ

高可用性:
  ☐ 3つのAZに6コピー
  ☐ 自動フェイルオーバー
  ☐ 最大15レプリカ

セキュリティ:
  ☐ VPC内配置
  ☐ TLS接続
  ☐ 暗号化（保管時・転送時）
```

### SAP試験重要ポイント

```yaml
高度:
  ☐ Change Streams活用

  ☐ 接続プーリング戦略
```
